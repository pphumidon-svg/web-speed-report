ปัญหาไม่ใช่ “เว็บหนัก” อย่างเดียว — ตัวการหลักคือเซิร์ฟเวอร์สร้างหน้าเว็บช้ามาก แต่ถูก Varnish cache บังไว้จนมองไม่เห็น

หน้าแรก · ไม่มีใน cache 2,404 ms
หน้าสินค้า · ไม่มีใน cache 4,664 ms

แท่งตามสัดส่วนจริง · เวลาที่เซิร์ฟเวอร์ตอบกลับ (TTFB) · วัดซ้ำ 3–4 รอบ ตัวเลขนิ่งทุกรอบ

แปลว่าอะไร: ทุกครั้งที่ cache ถูกล้าง — แก้สินค้า สต็อกเปลี่ยน ราคาเปลี่ยน มีออเดอร์เข้า — ลูกค้าคนถัดไปที่เปิดหน้านั้นต้องรอ 4.6 วินาทีก่อนเห็นอะไรบนจอเลย เว็บมีสินค้าหลายร้อยหน้า คนที่กดมาจากโฆษณา TikTok หรือ Google จึงมีโอกาสสูงมากที่จะตกหน้าที่ cache เย็น ถ้าแก้ได้แค่ข้อเดียว ให้แก้ข้อ 1

01

เซิร์ฟเวอร์ใช้เวลา 4.6 วินาทีสร้างหน้าสินค้า

ผลกระทบสูงสุด ต้องเข้า Cloudways เริ่มได้ทันที
หลักฐาน หน้าสินค้า cache miss  4,643 ms / 4,664 ms
หน้าแรก cache miss     2,344 ms / 2,370 ms / 2,404 ms
หน้าเดียวกัน cache hit   61–162 ms
  • เปิด Redis Object Cache — Cloudways มีให้ใช้อยู่แล้วใน Application Settings แล้วติดตั้งปลั๊กอิน Redis Object Cache ปกติลด TTFB ได้ 40–60% นี่คือของฟรีที่ยังไม่ได้ใช้
  • ยืนยันว่าใช้ PHP 8.2 หรือ 8.3 และเปิด OPcache แล้ว
  • ติดตั้ง Query Monitor ชั่วคราว เปิดหน้าสินค้าดูว่า query ไหนกินเวลา และปลั๊กอินไหนเป็นเจ้าของ
  • ทดสอบปิด advanced-dynamic-pricing-for-woocommerce แล้ววัด TTFB ซ้ำ — ปลั๊กอินตัวนี้คำนวณราคาใหม่ทุกสินค้าทุก request เป็นสาเหตุคลาสสิกของหน้าสินค้าช้า
  • ตั้ง cache warming ให้ cron ไล่ crawl product-sitemap.xml ทุกครั้งหลัง cache ถูกล้าง เพื่อไม่ให้ลูกค้าเจอหน้าเย็น
  • ทบทวนกฎ purge — อย่าให้แก้สินค้า 1 ชิ้นแล้วล้าง cache ทั้งเว็บ
02

รูปทุกรูปถูกแทนด้วย placeholder รวมถึงโลโก้และแบนเนอร์แรก

กระทบคะแนน Google โดยตรง แก้ง่าย
หลักฐาน Breeze lazy load เปลี่ยน src ของรูปทั้ง 92 รูป เป็น
data:image/svg+xml;base64,... แล้วเก็บ URL จริงไว้ใน data-breeze
รูปที่มี fetchpriority="high" ก็โดนด้วย

รูปหลักจึงยังไม่เริ่มดาวน์โหลดจนกว่า JavaScript จะทำงานเสร็จ ค่า LCP ที่ Google ใช้ตัดสินอันดับพังตรงจุดนี้

  • Breeze → Lazy Load → ยกเว้น โลโก้ + แบนเนอร์ hero + รูปสินค้า 4 ชิ้นแรก
  • ใส่ fetchpriority="high" และ <link rel="preload"> ให้รูป LCP
  • ทางที่ดีกว่า: เลิกใช้ JS lazyload ทั้งหมด ใช้ loading="lazy" ของเบราว์เซอร์แทน ซึ่ง WordPress ใส่ให้อยู่แล้ว ปลอดภัยกว่าและไม่ต้องรอ JS

ฟอนต์ไทยหนักกว่าฟอนต์อังกฤษหลายเท่า เพราะต้องมีวรรณยุกต์และสระครบชุด การโหลด 5 ตระกูลพร้อมกันจึงแพงมาก

  • ตัดเหลือฟอนต์ไทย 1–2 ตระกูล และเฉพาะน้ำหนักที่ใช้จริง (ปกติ 400 + 600 พอ)
  • ลบ Font Awesome จาก cdnjs ออก — ซ้ำกับที่ Elementor มีอยู่แล้ว ตัด external host ไปได้ 1 ตัว
  • ถ้าใช้ไอคอนไม่กี่ตัว เปลี่ยนเป็น SVG inline จะประหยัดฟอนต์ไอคอนได้เต็ม 157 KB
  • ย้ายฟอนต์มา self-host ทั้งหมด ตอนนี้ยังดึงจาก fonts.googleapis.com อยู่ 1 จุด กินเวลา 426 ms
  • ใส่ font-display: swap และ preload เฉพาะฟอนต์หลักตัวเดียว

สคริปต์ภายนอกกินเวลา 1.2–1.3 วินาที และไม่มี preconnect เลย

ต้องคุยกับฝ่ายการตลาดก่อน preconnect ใส่ได้ทันที
เวลาที่วัดได้จริง Microsoft Clarity  z.clarity.ms/collect  1,269 ms · 829 ms (เรียก 5 ครั้ง)
TikTok Pixel     analytics.tiktok.com    787 ms (เรียก 7 ครั้ง)
Cookiewow       cookiecdn.com 500 ms + config 468 ms + โลโก้ S3 447 ms
Cloudflare Insights beacon  542 ms
  • ใส่ <link rel="preconnect"> ให้ 4 host: googletagmanager.com, analytics.tiktok.com, clarity.ms, cookiecdn.com — ตอนนี้ไม่มีเลยสักตัว
  • รวมทุกอย่างให้ยิงผ่าน GTM ตัวเดียว อย่าฝัง script ตรงในธีม
  • ตั้ง trigger ของ Clarity และ TikTok Pixel เป็น Window Loaded หรือหน่วงจนผู้ใช้ scroll ครั้งแรก (Perfmatters มีฟีเจอร์ Delay JavaScript) — ตัวเลข conversion ไม่หาย เพราะยิงหลังหน้าโหลดเสร็จ
  • พิจารณา ปิด Clarity ถ้าไม่ได้เข้าไปดู heatmap จริงจัง — ตัวนี้แพงสุดในกลุ่ม

หน้าแรกยัดสินค้า 62 ชิ้น ทำให้ HTML บวมเป็น 1 MB

ต้องให้ฝ่ายการตลาดตัดสิน ช่วยข้อ 1 ไปในตัว
หลักฐาน HTML หน้าแรก 1,078,424 ตัวอักษร · DOM 4,699 โหนด
สินค้าบนหน้าแรก 62 ชิ้น · สินค้าที่เกี่ยวข้องในหน้าสินค้า 11 ชิ้น
  • ลดสินค้าหน้าแรกเหลือ 20–24 ชิ้น แล้วใส่ปุ่ม “ดูสินค้าทั้งหมด”
  • ลดสินค้าที่เกี่ยวข้องในหน้าสินค้าจาก 11 เหลือ 4–6 ชิ้น
  • ผลพลอยได้: เซิร์ฟเวอร์สร้างหน้าเร็วขึ้นด้วย ช่วยแก้ข้อ 1 ไปในตัว

ลำดับลงมือ

สัปดาห์ที่ 1 ของฟรี ผลเยอะ ความเสี่ยงต่ำ · ทำบน production ได้
  • เปิด Redis Object Cache บน Cloudways + ติดตั้งปลั๊กอิน
  • ยืนยัน PHP 8.2+ และ OPcache เปิดอยู่
  • ยกเว้นโลโก้ + แบนเนอร์ hero ออกจาก Breeze lazy load
  • ลบ Font Awesome ตัวซ้ำจาก cdnjs
  • ใส่ preconnect ให้ host ภายนอก 4 ตัว
  • ปิด cart fragments นอกหน้าตะกร้าและ checkout
สัปดาห์ที่ 2 ต้องทดสอบบน staging ก่อนทุกข้อ
  • หา slow query ด้วย Query Monitor และทดสอบปิด Advanced Dynamic Pricing
  • ติดตั้ง Perfmatters ปิด asset รายหน้า + หน่วงสคริปต์ analytics
  • ตัดฟอนต์เหลือ 1–2 ตระกูล และย้ายมา self-host
  • ลดสินค้าหน้าแรกเหลือ 24 ชิ้น
สัปดาห์ที่ 3 งานโครงสร้าง ป้องกันไม่ให้ปัญหากลับมา
  • ตั้ง cache warming ให้ crawl sitemap อัตโนมัติหลัง purge
  • ทบทวนกฎ purge ไม่ให้แก้สินค้า 1 ชิ้นล้าง cache ทั้งเว็บ
  • ย้าย Elementor CSS ไปเป็น External File
  • วัดผลซ้ำทั้งชุด แล้วเทียบกับตารางเป้าหมายด้านล่าง

วัดก่อนและหลังทุกครั้งด้วย PageSpeed Insights (โหมด Mobile) แต่ตัวที่สำคัญกว่าคือ Core Web Vitals ใน Google Search Console เพราะเป็นข้อมูลผู้ใช้จริงย้อนหลัง 28 วัน ไม่ใช่การจำลอง — ตัวเลขจะขยับตามหลังการแก้ประมาณ 2–4 สัปดาห์

ข้อจำกัดของการตรวจครั้งนี้

  • วัดจาก network ภายนอกผ่าน Cloudflare edge กรุงเทพฯ ไม่ใช่ Lighthouse lab test เต็มรูปแบบ
  • ไม่ได้เข้าถึง WordPress admin และ Cloudways จึง ยังยืนยันไม่ได้ว่า Redis เปิดอยู่หรือยัง และใช้ PHP เวอร์ชันอะไร — สองข้อนี้ทีมต้องเช็คให้
  • ข้อสงสัยเรื่องปลั๊กอิน Advanced Dynamic Pricing เป็น สมมติฐานจากรูปแบบอาการ ยังไม่ใช่ข้อสรุป ต้องพิสูจน์ด้วย Query Monitor ก่อนตัดสินใจถอด
  • ค่า LCP และ CLS จริงต้องดูจาก Google Search Console เท่านั้น ตัวเลขในรายงานนี้เป็นค่าที่วัดจากเครื่องเดียว
